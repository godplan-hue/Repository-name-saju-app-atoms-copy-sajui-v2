## 1. ⚠️ 문제앱 정정 — 타로 아니고 사주+궁합이었음

사용자가 이전 보고("두 앱 다 저장 안 됨")를 타로+궁합으로 착각하고 지시했었는데, 실제로는 **사주+궁합**이 문제였고 **타로는 원래부터 저장이 잘 되고 있었음**. 사용자가 뒤늦게 정정: "궁합이랑 사주였는데 내가모르고 타로라고말햇지, 타로는 저장잘되고잇엇는데".

**결과**: [[project_session_2026_08_25d]]에서 타로에 적용한 3회재시도 수정(`285bf1d`)은 불필요한 작업이었음(해롭지는 않음). 궁합 수정(`c8f292f`)은 타로와 같은 이유로 했지만 결과적으로 맞는 앱이었음.

**How to apply**: 사용자가 "두 앱"처럼 앱을 지칭할 때 이름을 명확히 안 부르면 반드시 어떤 앱인지 되물어 확인할 것 — 이번에 잘못 짚어서 엉뚱한 앱(타로)에 먼저 작업하고, 진짜 문제앱(사주)은 뒤늦게 발견함.

## 2. 사주(jeomun-saju) DB저장 진짜 원인 발견 + 수정 (commit `d2ea301`)

`handleFormSubmit()`(사주 폼 제출 시 실행)에서 `fbPut(...)` 저장 호출을 **await 없이** 호출하고, 바로 다음 줄에서 `showFullScreenAd(...)`(전면광고)를 띄우고 있었음. mbti 코드에 이미 있던 경고 주석("전면광고가 뜨면서 백그라운드 fetch가 끊길 수 있어")과 정확히 같은 위험 패턴 — 광고가 뜨면서 저장 fetch가 완료되기 전에 끊길 수 있음. `fbPut` 자체엔 3회 재시도가 있었지만, 애초에 함수 실행 자체가 광고 때문에 중간에 끊기면 재시도 로직까지 못감.

**수정**: `handleFormSubmit`을 `async`로 바꾸고, 저장 완료(또는 최대 7초 타임아웃) `Promise.race`로 기다린 뒤에 광고를 띄우도록 순서 변경 — mbti의 `postAnalyzeWithRetry` + `Promise.race([...,wait(7000)])` 패턴과 동일.

**Why**: 결과화면 진입 직전 "저장 안 됨" 신고의 실제 재현 조건은 정확히 이 타이밍 — 사용자가 정보 입력 후 바로 결과보기를 누르는 가장 흔한 경로에서 발생함.
**How to apply**: 새 토스 앱 만들 때 "저장 fetch 호출 직후 광고를 띄우는 코드가 있는지" 항상 먼저 grep해서 확인할 것. `await` 없는 저장호출 + 바로 다음 줄 광고 호출 조합은 이제 알려진 버그 패턴으로 취급.

## 3. 궁합(jeomun-gunghap) 저장 구조는 정상 확인

궁합은 저장(`for` 루프, await fetch)이 끝난 직후 바로 광고를 안 띄우고 성향 퀴즈(여러 문항) 단계를 거친 뒤에야 광고가 뜸 — 저장과 광고 사이에 사용자 입력 시간차가 자연히 있어 사주와 같은 레이스 컨디션이 아님. [[project_session_2026_08_25d]]의 3회재시도 수정으로 충분할 것으로 판단.

## 4. 다음 확인 필요

사주+궁합 두 앱 다 `.ait` 콘솔 재업로드 필요(사용자). 재업로드 후 실기기 재테스트로 최종 확인.
