### ⚠️ 정정 — 실제 결제는 1건, 이메일만 중복 발송된 버그 확인 (2026-08-29)
에스더님이 포트원(PG, NHN KCP) "통합 결제 내역"을 직접 확인한 결과, "욱"님 관련 **결제완료 건은 990원 1건뿐**(거래번호 `jeomun-1787979935481`, 주문명 "점운 사주 분석", 2026-08-29 14:06:04 상태승인) — 위에서 "2건 연속구매"라고 기록했던 것은 틀린 추정이었음. 실제로는 결제가 1번만 일어났는데 결제완료 처리 함수가 두 번 호출되면서 알림 이메일만 8초 간격으로 2통(상품명 "운세"/"결혼사주") 나간 것.

- **정정된 매출**: 1,980원이 아니라 **990원 1건**
- **의심 원인**: `app/main-v2/pay/page.tsx`의 `finalizeSuccess`(paymentId 형식 `jeomun-${Date.now()}`, package 고정값 "운세")와 `app/main-v2/payment/page.tsx`의 `finalizeModalPaymentSuccess`(paymentId `pay_...`/`jeomun-toss-...`, package는 `orderName` 동적값)가 **같은 결제 건에 대해 중복 호출**된 것으로 추정 — `payment/page.tsx`는 페이지 로드 시 `sessionStorage`/`localStorage`의 `pay_pending`이 남아있으면 `useEffect`에서 자동으로 `finalizeModalPaymentSuccess`를 다시 호출하는 구조라, 리다이렉트 결제 흐름에서 이 값이 제때 지워지지 않으면 완료 처리가 두 번 실행될 수 있음 (완전히 확정된 원인은 아니며 코드 추가 확인 필요)
- `app/api/v2/save-payment/route.ts`는 Firebase `v2_direct_payments/{id}`에 `.set()`(덮어쓰기)으로 저장하는데, 두 호출의 `id`(paymentId)가 서로 다르면 실제로는 레코드가 2개 만들어질 수도 있음 — 그런데 어드민 결제내역엔 1건만 보였다는 건 둘 중 하나가 애초에 DB 저장까지 안 갔거나(예: 이메일 발송 로직만 별도로 두 번 탄 경우), 혹은 같은 id로 겹쳤을 가능성 — **근본 원인은 아직 100% 확정 안 됨, 수정 여부는 에스더님 지시 필요**

**Why**: PG 결제내역이라는 1차 소스로 직접 대조해 "이메일 2통 = 실제 결제 2건"이라는 잘못된 결론을 바로잡음. 광고 ROI/매출 집계 시 이메일 건수가 아니라 PG 결제내역이나 어드민 결제내역을 기준으로 삼아야 함.
**How to apply**: 향후 결제 관련 매출을 볼 때 이메일 알림 건수를 그대로 신뢰하지 말고 PG 통합결제내역 또는 어드민 결제내역으로 재확인할 것.

### ✅ 근본원인 확정 + 수정 완료 (2026-08-29)
`app/main-v2/payment/page.tsx`의 PortOne 리다이렉트 감지 `useEffect`(결제완료 자동처리)가 **URL의 `paymentId`와 저장된 `pay_pending`의 `paymentId`가 같은지 검증하지 않고** "URL에 paymentId 있음 + 저장소에 pay_pending 아무거나 있음"만으로 결제 성공 처리를 하고 있었음. 이 페이지(`/main-v2/payment`)에서 파는 모든 990원~4900원 상품(신년운세/연애사주/내사람찾기/결혼사주/이혼운세/대운/연도별운세/재회운 등, 전부 같은 `openPortoneModal`→`portoneModalPay` 경로 공유)이 동일하게 취약했음 — "결혼사주"만의 문제가 아니었음.

즉 예전에 중간에 그만둔 결제 시도의 `pay_pending`이 로컬저장소(localStorage, 세션 종료돼도 안 지워짐)에 남아있다가, 나중에 실제 다른 결제(사주 990원 등)가 완료되며 URL에 paymentId가 붙는 순간 이 오래된 pay_pending과 우연히 짝지어져 "성공"으로 잘못 처리된 것으로 결론. 이래서 실결제 1건인데 완료처리 함수가 2번(운세+결혼사주) 실행되어 이메일도 2통 가고, DB에도 결혼사주가 결제완료로 잘못 찍힘 — 그리고 결제 없이 결혼사주 결과 페이지까지 열람했을 가능성 높음(완료처리 함수가 결과페이지로 자동 리디렉션시키는 구조라서).

**수정 내용**: `payment/page.tsx`의 해당 useEffect에 `if (info.paymentId !== pgPaymentId) return;` 한 줄만 추가 — URL의 paymentId와 저장된 paymentId가 정확히 일치할 때만 결제완료 처리하도록 검증 추가. 정상 결제 흐름은 항상 두 값이 같으므로 기존 작동 중인 결제(사주 990원 등)에는 영향 없음. `pay/page.tsx`, `save-payment/route.ts` 등 다른 파일은 전혀 건드리지 않음 — 에스더님이 결제저장 로직이 막 안정화된 상태라 다른 파일 손대지 말라고 명시적으로 요청함.

**Why**: 정확한 재현 조건(오래된 pay_pending + 우연한 paymentId 매칭)까지 규명해서, 이 페이지에서 파는 다른 상품들도 같은 버그에 노출돼 있었다는 걸 확인함.
**How to apply**: `/main-v2/payment` 페이지에 새 상품을 추가하거나 결제 흐름을 수정할 때, 이 paymentId 일치검증이 유지되고 있는지 반드시 확인할 것. 유사한 검증 누락이 `pay/page.tsx`의 리다이렉트 감지 로직에도 잠재적으로 있을 수 있으나(같은 패턴), 에스더님 지시로 이번엔 손대지 않음 — 재발하거나 다음에 결제 안정화 작업할 때 참고.
