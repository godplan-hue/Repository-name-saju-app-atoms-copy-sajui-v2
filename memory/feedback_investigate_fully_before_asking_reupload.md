토스 미니앱 버그 수정 시, 확신 없는 상태로 부분수정→재업로드 요청→테스트→또 다른 원인 발견→재수정→재업로드 요청 을 반복하면 안 됨.

## 사건 (2026-08-25, 대운 광고버그)

대운 "지금 열어보기" 광고 안 뜨는 버그를 고치면서:
1. adImpression 조건 제거 (`da007d5`) → 재업로드 요청 → 여전히 안됨
2. failedToShow/onError 재적재 누락 수정 (`bd1572d`) → 재업로드 요청 → 여전히 안됨
3. 프리로드 추가 (`48ee5cd`) → 재업로드 요청 → 사용자가 테스트하는 도중에
4. SDK 소스 직접 읽어서 "loaded" 이벤트 기반 정확한 준비상태체크로 재수정 (`35fb2d2`) → 또 재업로드 요청

사용자가 "좀 대때 잳때 수정해 사람 몇십번 테스트하게 하지말고" (한번에 제대로 고쳐라, 몇십번 테스트시키지 마라)라며 강하게 항의함.

## Why

토스 미니앱은 코드수정 → 빌드 → 콘솔 업로드 → 실기기 테스트 전체 사이클을 사용자가 수동으로 반복해야 함(내가 대신할 수 없음). 매번 "일단 이거 고쳤으니 올려보세요" 식으로 부분수정만 내놓으면 사용자가 반복노동을 떠안게 됨.

## How to apply

- 광고/공유링크 등 SDK 관련 버그는 재업로드 요청하기 전에 **관련 함수 전체 + SDK 소스(prebuilt JS)를 먼저 다 뒤져서 이벤트 시퀀스/실패조건을 끝까지 확인**한 뒤 한번에 수정할 것
- "일단 이것부터 고쳐보고 안되면 또 보자" 식 점진적 수정-재업로드 요청 금지
- 확신이 서지 않으면 재업로드 요청 전에 코드 검증을 몇 단계 더 거칠 것 (grep으로 SDK 이벤트타입 확인 등, [[bug_daewoon_adimpression_instant_unlock_2026_08_25]] 에서처럼)

## 추가 사건 (2026-08-25, 타로 공유버튼) — 코드 문제가 아니라 리뷰 미승인이었던 케이스

타로 공유버튼이 "고객센터에 문의하세요" 에러를 계속 낸다고 해서 코드(딥링크 스킴)만 계속 다시 확인함. granite.config appName과 intoss:// 스킴이 이미 정확히 일치(둘 다 tarot-jeomun)하는데도 계속 에러 재현됨 → deploymentId만 바꿔 재빌드 요청 → 여전히 안됨 → 결국 사용자가 "앱 출시" 화면 스크린샷을 보내서야 확인: **오늘 만든 버전 16개가 전부 "검토 필요"/"요청 취소됨" 상태, 승인된 게 하나도 없었음.** 즉 코드는 처음부터(faac20c) 이미 맞았고, 실제로는 어떤 수정본도 토스 리뷰를 통과해 라이브로 나간 적이 없어서 무슨 수정을 해도 테스트에 반영될 수 없었던 것 — 순수 리뷰 파이프라인 문제였는데 코드 버그처럼 계속 재조사/재빌드를 요청함.

## How to apply (추가)

- "공유버튼/딥링크가 안 된다", "존재하지 않는 앱 에러" 같은 신고를 받으면, 코드(스킴 매칭)부터 파기 전에 **먼저 앱인토스 콘솔 "앱 출시" 메뉴에서 최신 버전이 실제로 "승인"·"출시" 상태인지부터 확인 요청할 것.** "검토 필요"/"요청 취소됨" 상태면 그 어떤 코드 수정도 라이브에 반영이 안 되므로 코드를 다시 뒤지는 건 시간 낭비.
- 즉 진단 순서: ① 콘솔에 실제 라이브(승인+출시)된 버전이 있는지 먼저 확인 → ② 없거나 옛날 버전이면 그게 원인 → ③ 그래도 최신 버전이 라이브인데 안 되면 그때 코드를 판다.
