## Part 2. Niche 발견 및 브랜드 기획

**4단계 Fit 진단 프레임워크 (각 6문항)**: User Fit(유저층 존재·접근가능?) → Desire Fit(절실히 원하는가?) → Founder Fit(창업자 배경과 맞는가?) → Product Fit(지금 리소스로 실제 해결 가능한가?)

- **사주아이 적용**: User Fit=2030 여성층 명확, Desire Fit="오늘의 운세" 반복소비 습관성, Founder Fit=창업자 개인 관심사 일치, Product Fit=API 없이 템플릿으로도 "AI처럼" 구현 가능(점운의 핵심전략과 동일).
- **미국 자동차 리스 협상 툴 사례**: 비영어권 이민자 창업자가 본인 경험(정보비대칭 피해)을 Founder Fit으로 활용.
- **추가 케이스**: mosery, 꼬끼오 알람, 콘서트가방/OvB, 노라보자, 범정부오피스 — 흔한 문제를 좁은 유저층에 맞춰 재정의하는 방식 예시.

## 사주아이 유료강의7-3 사주아이 앞으로의 방향

> 2026-08-11 추가. 에스더님이 직접 녹화해서 텍스트로 뽑은 강의 클립 9개 중 1번째 — 강의 마지막 클립(창업자의 향후 방향성·고민 공유).

- **바이브코딩 시대 = 만드는 건 쉬워졌고, 소비자 마음을 얻는 게 진짜 경쟁력.** 아이디어 자체의 가치는 떨어졌고, 홍수 속에서 소비자와 더 가깝게 다가가 마음을 얻는 사람이 승자.
- **우선순위 판단 2축 — 신규 유입 vs 리텐션.** 이번 업데이트/마케팅이 신규유저 타겟인지, 기존유저 재방문(특정 시간대 알람 등) 타겟인지, GA 데이터·트래픽 기준으로 항상 이 2축으로 판단.
- **속도 + 성능 = 경쟁력.** MCP와 생산성 툴을 적극 활용해 "혼자여도 팀처럼" 움직이고, 반복적인 일은 난이도 상관없이 무조건 자동화.
- **AI가 못하는 것 = 사람을 이해하는 일.** 유저 목소리 전달·기획·팀원 구하기 등 "사람만 할 수 있는 본질적인 일"에 창업자 본인의 시간을 집중.
- ⭐ **"지금 시대 가장 큰 병목은 나 자신이다."** 기술은 다 해결 가능해졌고, 유일한 병목은 창업자의 멘탈리티·번아웃·개인 상황(육아 등). 그래서 스스로를 지속가능하게 관리하는 것 자체가 전략.
- **방향성 3가지**: ① 계속 배우면서 자동화로 빠르게 갈 것 ② 시장·소비자 반응에 민감하게 반응할 것(기술 자체는 의미없고 시장에 먹히는지가 핵심) ③ **"나만의 메시지"를 스스로 찾아 제품으로 전달하는 데 가장 큰 의미를 둘 것.**

## 사주아이 유료강의5-1-1 문의처리 페이지

> 2026-08-11 추가. 강의 클립 9개 중 2번째 — PART 5(지속가능한 운영시스템) 첫 클립, "문의 처리 관리자 페이지 만들기". Part 5 전체는 필수 아니고 필요한 부분만 골라서 하면 되는 성격.

**전체 목적**: 오류 문의 + 피드백 두 종류를 유저에게서 받아서, 관리자만 볼 수 있는 대시보드에서 확인·처리하고, 새 문의가 오면 슬랙으로 실시간 알림을 받는 시스템.

**전체 흐름**
1. 유저가 홈페이지에서 오류 문의/피드백 작성
2. POST API(서버 단)를 통해 Firestore에 새 컬렉션(`inquiries`)으로 저장
3. 저장되는 순간 슬랙 웹훅(Webhook)이 트리거되어 알림 발생
4. 관리자가 알림 확인 → 어드민 대시보드 접속 → API 라우트로 목록을 안전하게 조회(인증된 관리자만)

**핵심 보안 원칙 (2가지로 확정)**
- ① 권한 검증은 무조건 서버에서 한다 — 클라이언트단 검증은 조작 가능해서 안 됨
- ② 관리자 판별도 로그인한 유저의 UID 기준으로 서버에서 확인한다
- (원래 3번째로 "어드민 주소를 예측 불가능한 임의 문자열로 만들기"가 있었으나, 어차피 서버에서 UID로 권한 검증하기 때문에 주소를 안다고 접속되는 게 아니라서 큰 의미 없다고 판단해 제외함)

**관리자 등록 방법 (추천 방식)**
- 두 가지 방법 중, Firebase Auth 자체 커스텀 클레임(태그) 방식보다 **Firestore에 UID를 직접 저장하는 방식**을 추천 — 이유: 나중에 관리자가 여러 명(가족, 알바생 등)이 될 때 각 관리자에 대한 부가정보(처리 기록 등)를 함께 관리하기 쉬움. 인증 속도는 클레임 방식이 조금 더 빠르지만 관리자 전용 페이지라 체감 차이 없음.
- 내 UID 찾는 법: ① Firebase 콘솔 → Authentication → Users 탭에서 이메일 옆 UID 복사, 또는 유저 수가 많아지면 검색창에 이메일 입력해 찾기 ② 로컬 개발 환경에서만 보이는 디버그용 UID 표시 기능을 만들어 로그인 시 화면/콘솔에 UID를 띄우는 방법
- 찾은 UID를 프롬프트에 붙여넣어 Claude에게 넘기면 Firestore `admins` 폴더(컬렉션)에 UID(+이메일, 선택)를 저장해줌

**문의하기 폼 구현**
- Next.js라 프론트+백엔드(API)+보안까지 한 번에 프롬프트로 생성 가능
- 기본값: 홈페이지 하단에 작게 표시됨. 더 눈에 띄게/특정 화면 위치에 넣고 싶으면 "어떤 위치에, 어떤 UX 단계에서 노출되면 좋겠다"를 프롬프트에 구체적으로 추가해야 함
- 기본은 "오류 문의"/"피드백" 2종류. 계좌이체 입금 확인 같은 커스텀 항목(계좌번호, 입금자명, 이메일 등)도 필요하면 프롬프트에 추가 요청하면 됨 — 사주아이는 초창기에 계좌이체 입금 확인 용도로 이 문의폼을 활용했음

**어드민 대시보드**
- 경로 예시: `/admin/inquiry` (꼭 이 이름 아니어도 무방, 어차피 UID 인증이 핵심이라 주소 자체는 안전과 무관)
- 등록된 관리자 UID로 로그인했을 때만 대시보드가 보이고, 그 외 계정은 접근 자체가 막힘
- 기본 제공 기능: 문의 내용 확인 + 처리완료 체크
- 유저에게 대시보드 안에서 직접 답장하는 기능은 기본에 없음 — 필요하면 프롬프트로 추가 요청해야 함. 사주아이는 답변 기능까지 만들어서 제공. 서비스 초반엔 답변 없이 "받기만" 하고 끝내는 곳도 많음 — 운영 여력에 따라 결정하면 됨

**슬랙 알림 연동 (이메일보다 슬랙 추천)**
- 이유: ① 완전 무료 ② 여러 명(팀)이 실시간으로 같이 확인 가능 — 이메일은 보통 1인 전용이라 팀 단위 확인이 어려움 ③ 연동 난이도도 더 쉬움
- 연동 절차: Slack API 사이트에서 앱 생성 → 로그인 후 왼쪽 메뉴 "Incoming Webhooks" 활성화 → 워크스페이스에 앱 추가 → 알림 받을 채널 생성/선택 → Webhook URL 발급
- ⚠️ 이 Webhook URL은 비밀 값이므로 프롬프트에 직접 붙여넣지 말고, `.env.local`에 `SLACK_WEBHOOK_URL` 같은 키로 저장한 뒤 프롬프트로 "이 환경변수 이용해서 연동해줘"라고 요청할 것
- 연동되면 유저가 문의 등록 시 즉시 슬랙 알림이 옴

**사주아이의 고도화 사례 (참고용, 처음부터 다 할 필요 없음)**
- 오류 문의 들어오면 대시보드 안에서 바로 "사주 재생성"을 눌러 처리
- 재화("추르") 충전이 잘 안 된 문의는 대시보드에서 바로 추르 충전 처리
- 이후 지인 중심으로 CS팀을 꾸려 시간대별 모니터링 분담 + 누가 얼마나 처리했는지 보는 별도 통계 대시보드까지 확장

**다음 클립 예고**: 구글 애널리틱스(GA) 파이프라인 설계

**How to apply (점운):** 점운은 이미 알림톡(솔라피)·admin 패널이 있지만, 슬랙 실시간 알림 방식은 없음. 나중에 문의량이 늘면 이 구조(Firestore `admins` UID 저장 + 서버단 권한검증 + 슬랙 웹훅)를 그대로 참고해서 붙이면 좋을 것 같음. 지금 당장 급한 건 아니니 에스더님이 필요하다고 판단할 때 진행.

## 사주아이 유료강의5-2 GA파이프라인 설계 (중요)

> 2026-08-11 추가. 강의 클립 9개 중 3번째 — PART 5, "GA(Google Analytics) 파이프라인 설계". 에스더님이 "중요"라고 직접 표시함.

**목적**: Firebase를 통해 기본 통계(누가, 언제, 어디서, 얼마나 오는지)를 자동 수집하는 구조. 데이터를 모으기 전에 "어떤 정보를 모으고 싶은지"부터 먼저 설계하는 게 순서.

**수집 가능한 핵심 지표**
- **기본 방문 지표**: DAU(일간 방문자)/WAU(주간)/MAU(월간), 리텐션(재방문 빈도), 평균 체류시간 — 이 정도는 GA 연결만 해도 거의 자동으로 수집됨
- **유입 경로**: 공유 페이지/홈페이지/이벤트 등 어디서 들어오는지 — 어떤 페이지를 더 강화해야 할지 판단 근거가 됨
- **유입 시점**: 월초/월말, 시간대별 타임스탬프로 언제 몰리는지
- **(심화) 이탈 지점**: 특정 단계부터 카운트가 뚝 끊기면 그 지점에서 이탈로 간접 추정 가능
- **(심화) 전환 트래킹**: 특정 액션을 이벤트로 심어서 "구매까지 가는지" 등을 추적
- **매출/상품 데이터**: 상품이 여러 개면 어떤 상품에서 매출이 주로 나는지(통화·가격·상품종류 설정)
- **클릭 이벤트**: 특정 버튼/기능을 얼마나 클릭하는지도 개별로 트래킹 가능

**GA vs 포스트호그(PostHog)**
- GA는 기본 통계(방문자수, 유입경로, 전환 등) 수집용, 무료
- 히트맵이나 더 깊은 유저 행동 분석이 필요하면 유료 서비스인 **포스트호그**를 추가로 사용 — 사주아이는 GA + 포스트호그 둘 다 사용 중
- 바이브코딩 초반 단계에서는 GA만으로 충분하다고 조언

**연동 방법**
1. Firebase 콘솔 → 프로젝트 선택 → 왼쪽 메뉴 "애널리틱스" → 사용 설정 (설정만 하면 구글 애널리틱스가 자동 연결됨)
2. 왼쪽 위 톱니바퀴 → 프로젝트 설정 → "일반" 탭 → 아래로 스크롤해서 앱 SDK 설정 확인
3. 여러 변수 값 중 맨 마지막 `measurement id` (대문자 G로 시작하는 값)를 복사
4. 이 값은 **공개값**이라 그대로 프롬프트에 넣어도 됨 (Slack Webhook URL과 달리 비밀값 아님) — 프롬프트의 `G-XXXXXXX` 자리에 붙여넣고 Claude에게 전달
5. Claude가 회원가입/로그인/구매 등 핵심 액션에 통계 수집 코드를 "심어줌" — 기본 프롬프트는 기본적인 이벤트만 포함하므로, 콘솔 보면서 더 필요한 이벤트가 있으면 추가 요청

**대시보드에서 볼 수 있는 것 (실제 사주아이 예시)**
- DAU/WAU/MAU 3종 + 최근 30분 활성 사용자 수
- 활성 사용자당 평균 사용 시간, 시간대별 유입자 수
- 페이지별 조회수(이벤트 페이지뷰 수)
- "더보기"로 들어가면 더 자세한 보고서(비교 옵션 등)도 가능하지만, 초반엔 "몇 명 들어오는지 + 유저 흐름" 정도만 봐도 충분하다고 조언
- (참고 수치, 사주아이 비수기 기준) DAU 4.3만 / WAU 20만 / MAU 58만, 최근 사용자 약 1800명 — 사주아이는 165만 누적 유저 규모라 절대값이 크므로 점운과 직접 비교할 수치는 아님, 흐름 파악용 참고

**다음 클립 예고**: 프롬프트(AI) 생성 시 드는 비용을 트래킹하는 방법

**How to apply (점운):** 점운은 GA/Firebase 이미 붙어있는지 다음 세션에서 코드로 먼저 확인 필요([[feedback_check_code_not_docs]] 원칙). 아직 없다면 이 순서(콘솔에서 애널리틱스 사용설정 → measurement id 복사 → 핵심 이벤트 프롬프트로 요청)를 그대로 적용하면 됨 — SEO 유입이 늘고 있는 지금 시점에 DAU/유입경로를 보기 시작하면 어떤 앱·랜딩이 실제로 트래픽을 끌어오는지 판단하는 데 도움될 것 같음.

## 사주아이 유료강의7-2-1 팀원 필요한가

> 2026-08-11 추가. 강의 클립 9개 중 4번째 — PART 7, "팀원이 꼭 필요한가?"에 대한 창업자 인사이트(정답은 아니고 본인 경험 공유라고 전제).

**핵심 자가진단 질문**: 지금 병목이 "사람"인가 "AI"인가?

**사람이 병목일 때 → AI 자동화를 먼저 할 것**
- 의미: 대표 본인이 의사결정을 늦게 하거나, 우선순위에 밀려 못 하고 있는 상태
- 반복적이고 규칙이 있는 일이 계속 밀린다면, 사람을 뽑기 전에 그걸 대신할 AI 자동화 방법이 분명히 있음
- 개발·운영도 코덱스/커서/클로드 같은 MCP 도구로 상당 부분 대체 가능
- ⚠️ 지금 병목이 생겼다고 바로 사람을 뽑으면, 그 사람과의 소통·체크 자체가 새로운 병목이 됨 (그 사람도 결국 AI를 활용해야 하는 건 마찬가지)
- 결론: 자동화로 풀 수 있는 문제는 자동화로 풀고 계속 배워나가는 게 우선

**AI가 병목일 때 → 사람이 필요할 수 있음**
- 의미: 특정 시점에 퀄리티가 안 올라옴 — "해줘"라고 했는데 AI가 못 해주는 지점, 아직 인간 기술의 한계가 있는 영역
- 사람의 스페셜티가 꼭 필요한 영역 예시: 디자인, 사람과의 네트워크/신뢰 관계, 콘텐츠 기획(유저 파악), B2B 영업·협업, 공격적/적극적 마케팅(MCP 툴 세팅 자체도 일)
- 판단이 필요한 결정은 대표가 주로 하되, 도와줄 코파운더나 깊은 전문성이 필요한 경우도 있음
- **채용 기준**: "AI로 안 되는 일을 할 사람"을 뽑는 것

**사주아이 팀의 실제 협업 방식**
- 팀원들 시간대가 다 다름(한국·미국 등 거주지 상이) → 절반 이상 리모트, 비동기 근무 — "9 to 6 루틴"이 아니라 시스템으로 돌아가는 구조
- **슬랙**: 텍스트로 대화, 이슈 생기면 채널/티켓 만들어 브레인스토밍, 급하면 허들(음성)로 바로 소통, 스레드로 기록 남김
- **게더(Gather) 버전2**: 가상 오피스 — 같은 공간에 있다는 느낌을 위해 사용, 각자 책상에 앉아있다가 옆에 가서 말 걸거나 회의실 들어가서 회의, 전체 회의도 게더에서 진행
- **업무관리툴**: 지라·아사나도 써봤지만 최근엔 **리니어(Linear)**로 정착 — MCP 연동이 잘 되어있고 직관적(누가 뭘 관리하는지, 어떤 사이클로 운영되는지 한눈에 보임)
- **자동화 도구 역할 분담**: 클로드=UI/UX 빌딩, 코덱스=디버깅, 커서=토큰 부족할 때 보완/커서 내 기능용
- **위스퍼 플로우(Whisper Flow)**: 말하면 프롬프트 텍스트로 변환해주는 툴 — 크리에이티브한 일은 타이핑보다 말로 하는 게 생각이 더 잘 이어져서 애용 중(목은 아프지만 손가락은 편함). 레니스 뉴스레터 구독하면 할인 받을 수 있음
- **통합 워크플로우**: 슬랙에서 대화하다가 "이건 이렇게 일하면 되겠다" 싶으면 슬랙 안에서 리니어 MCP 봇을 불러 이슈로 정리/완결 처리 → 코덱스·클로드가 리니어 MCP를 불러와서 새 이슈를 보고 직접 코드 구현 → 리뷰 상태로 둬서 사람이 검증 — 이 흐름을 빠르게 구현하는 데 지금 집중하고 있음
- 기타 사용 툴: 노션, 그레놀라(영어 회의 대비), 피그마, 깃허브, 비트워든(보안). 비용 부담이 크므로 에브리원·레니스 뉴스레터 같은 구독 할인 채널 적극 활용

**사람 채용 시 법적 리스크 (중요 — 노무 관련)**
- 계약서상 "프리랜서"라도 실질적으로 근로자성이 인정되면 법적으로는 근로자임. 판단 기준 예시: 출퇴근을 한다, 지시에 따라 업무를 한다, 완전히 독립된 프로젝트 단위가 아니다, 장기간 고정적으로 일한다, 특정 업무를 꾸준히 맡는다 등
- 근로자성이 인정되면 사대보험 가입 + 근로계약 체결이 법적으로 필요함
- **실제 사례(경고성)**: 프리랜서 계약으로 4~5명을 수년간 고용한 회사에서 그중 한 명이 노동청에 신고 → 노동청이 그 기간 전체 사대보험료 + 세금을 한 번에 부과. 원래 사대보험은 회사·근로자가 50%씩 부담해야 하는데, 노동청이 일괄 부과하면서 회사가 100%를 떠안게 됨 → 그 회사는 결국 파산했다고 전해 들음
- **권장 대응**: 실질이 근로자라면 처음부터 근로계약을 체결하되, 법적으로 허용되는 **수습 기간**을 두어 서로 핏을 맞춰보고 정식 계약 여부를 판단할 것. 노무 관련은 반드시 노무사와 상담할 것(본인도 노무 전문가가 아니라고 전제)

**딱 맞는 사람을 구하는 법 — 공고보다 직접 찾아나서기**
- 공고 지원자가 핏이 안 맞을 가능성이 높은 이유: 공고를 낸 사람이 어떤 사람을 원하는지 지원자가 정확히 모르고, "일단 넣어본" 지원일 가능성이 높으며, 중간에서 검증·보증해줄 사람이 없어 신뢰 판단이 어려움
- 본인 방식은 **직접 찾아나서는 것** — 헤드헌터에게 추천받고 그 사람과 대화하며 또 다른 사람을 소개받거나, 이미 특정 분야에서 잘하고 있는 사람에게 직접 같이 일하자고 제안
- 공식 공고 루트보다 **링크드인 등에서 미리 네트워킹하며 관계를 쌓아두는 방식**이 훨씬 핏이 잘 맞았다고 함 — 예: 실제로 같이 일하기 몇 개월 전부터 미리 알아가면, 함께 일을 시작하는 날("데이원")부터도 이미 합이 잘 맞는 느낌이 있었다고 함
- 팀 빌딩이나 코파운더를 장기적으로 고려하고 있다면, 필요하다고 생각되는 분야에서 일하는 사람들을 미리미리 만나두는 것을 추천

**마무리 요약**: 병목이 사람이면 AI로 풀고, 병목이 AI라면 그때는 사람이 필요할 수 있다. (다음이 마지막 클립이라고 예고)

**How to apply (점운):** 에스더님은 지금 거의 혼자 모든 걸 하고 계신데, 이 클립 기준으로 보면 지금 점운의 병목은 "AI가 못 해주는 부분"(홍보·영업·파트너 관계·의사결정 피로) 쪽에 더 가까워 보임 — 사람을 구한다면 반복적인 개발/운영 업무보다는 마케팅·파트너 영업·CS처럼 관계·판단이 필요한 영역이 우선순위일 것 같음. 다만 프리랜서 채용 시 노무 리스크(근로자성 인정 사례) 부분은 실제로 사람을 쓰게 될 때 꼭 다시 참고할 것.

## 사주아이 유료강의5-3 보안점검

> 2026-08-11 추가. 강의 클립 9개 중 5번째 — PART 5 마지막 클립, 바이브코딩 보안점검 체크리스트(약 14가지).

**배경**: 바이브코딩은 태생적으로 보안에 취약할 수밖에 없음 — 아무리 좋은 모델을 써도(해킹·보안에 특화된 모델이 아닌 이상) AI가 생성한 코드에 취약점이 있을 수 있음. 그래서 보안 점검은 필수. 방법: 아래 체크리스트 프롬프트를 클로드 코드에 붙여넣고, 모르는 보안 용어는 반드시 클로드에게 설명을 요청해서 "왜" 고쳐야 하는지 이해하고 넘어갈 것 (그냥 적용만 하지 말 것).

**1. 하드코딩된 비밀정보 확인** — 비밀번호·API키가 코드에 그대로 박혀있지 않은지 확인. 비밀값은 구글 시크릿 매니저 같은 곳에 있어야 함. `.env.local`이 절대 깃허브에 올라가면 안 됨 — 한 번이라도 올라간 적 있으면 그 즉시 API 키를 재발급(교체)해야 함.

**2. 클라이언트 노출용 키 vs 서버 비밀 키 구분** — 파이어베이스 설정값처럼 "public"으로 시작하는 값은 클라이언트에 노출돼도 괜찮지만, 서버단 비밀 키는 반드시 시크릿으로 저장해야 함. 비슷해 보이는 키라도 명확히 구분해서 확인 필요.

**3. Firestore 보안 규칙 점검** — 규칙이 누구에게나 열려있으면 다른 유저의 데이터에 접근하거나, 무제한으로 리소스를 생성하거나, 인가되지 않은 DB 접근이 가능해짐. Firestore 규칙 파일을 클로드에게 붙여넣어서 인증된 사용자만 의도된 행동을 할 수 있는지 검증받을 것.

**4. 앱체크(App Check) 여부** — 선택 사항. 아주 초기 단계 앱이면 필수는 아니지만, 어뷰징이 걱정되면 켜는 걸 추천.

**5. 사용자 입력값 검증** — 검색창 같은 입력 필드가 SQL 인젝션류 공격(교묘한 입력값으로 의도치 않은 시스템 동작을 유발하는 공격)에 취약한지 점검. 실제로 이런 사고가 있었다고 언급. 클로드에게 입력값 살균(sanitization) 여부를 확인받을 것.

**6. 관리자 인증 취약점 재점검** — (클립2/9 문의처리 페이지에서 만든) 관리자 전용 접근 시스템의 인증 취약점을 다시 확인.

**7. `.gitignore` 점검** — `.env.local` 같은 비밀 파일들이 `.gitignore`에 제대로 등록돼있는지, 실수로라도 커밋될 수 없는 구조인지 확인.

**8. 외부 패키지·의존성 점검** — 바이브코딩은 패키지를 가볍게 설치하는 경우가 많음. 스팸성 패키지이거나 오염된(악성) 오픈소스 라이브러리는 아닌지, 최신 위협 정보 기준으로 점검.

**9. API 호출 권한 범위 점검** — 어떤 API가 호출 가능한지, 권한 설정이 과도하게 넓게 열려있지 않은지 확인.

**10. 로그·에러 노출 점검** — 상세 에러 메시지/로그가 개발 환경에서만 찍히고 배포(프로덕션) 환경에서는 노출되지 않는지 확인. 아니면 실서비스 브라우저 콘솔에 민감정보가 그대로 노출될 수 있음.

**11. 과금 유발 호출 횟수 제한(빌링 어뷰징 방지)** — AI API 호출, 문자(SMS) 발송처럼 비용이 발생하는 기능에 호출 횟수 제한이 있는지 확인. 없으면 공격자가 무제한으로 호출을 트리거해서 요금을 폭증시키는 공격(빌링 어택)이 가능함.

**12. 외부 데이터를 검증 없이 AI에 그대로 넣지 않기** — 웹 스크래핑 등으로 가져온 외부/비신뢰 데이터를 검증 없이 그대로 AI에 넣어 처리시키는 코드가 있으면 위험함(예상치 못한 출력/행동 유발 가능) — 반드시 검증 후 AI에 넣을 것.

**13. URL에 민감정보·토큰 노출 여부** — 바이브코딩에서 매우 흔한 취약점. 로그인·리다이렉트 흐름에서 인증 토큰이나 개인정보를 URL 파라미터로 그대로 넘기면 중간에서 탈취될 위험이 있음. 실제 사례로 방송통신대학교에서 URL의 학번 파라미터를 바꾸면 다른 학생의 개인정보 페이지가 노출되는 취약점이 있었다고 언급(엄밀히는 파라미터별 인가 체크 누락이 원인이지만, "중요 정보를 URL에 넣지 말라"는 교훈은 동일). 토큰은 반드시 정식 인증 방식으로 전달하고 URL에 심지 말 것.

**14. 디도스(DDoS) 공격 대비** — 강사 본인이 실제로 디도스 공격을 받은 경험이 있다고 언급. 클라우드플레어(Cloudflare) 도입을 추천 — 여러 네트워크 계층에서 악성 트래픽을 걸러줌. 파이어베이스 앱호스팅 자체도 어느 정도 기본 방어는 되지만, 작정하고 뚫으려는 공격자는 우회할 수 있어서 클라우드플레어가 그 빈틈을 메꿔줌. 다만 클라우드플레어를 거치면 사용자 진입 시 검증(체크) 단계가 하나 더 생겨서 UX·전환율에 영향 줄 수 있음 — 특히 초기 저트래픽 서비스는 가장 중요한 진입 지점에서 마찰이 생길 수 있으니, 트래픽·공격 위험이 실제로 커진 뒤 도입해도 됨. 무료 플랜에도 포함돼있고 유료 플랜도 비싸지 않음. 실제로 디도스 공격을 받으면 신고는 한국에서 **법적 의무**임(신고센터가 적극적으로 도와주진 않는다고 알려져 있지만, 신고 자체는 의무). 마무리 발언: "결국 내 서비스는 내가 스스로 지켜야 한다."

**마무리**: 약 14가지 항목을 다뤘고, 이 외에 추가로 점검할 게 있는지는 클로드에게 직접 물어보길 권장. 이걸로 PART 5가 마무리됨. **다음 클립 예고**: PART 6, 초기 마케팅 — MVP가 만들어졌다는 가정 하에 사주아이가 초반에 SNS 채널을 어떻게 활용해 바이럴을 만들었는지에 대한 경험적(비체계적) 마케팅 노하우.

**How to apply (점운):** jeomun.com은 CLAUDE.md 기준 이미 Cloudflare(AI 크롤러 차단 + SSL 전체엄격)가 적용돼있어서 14번 디도스 항목은 이미 상당 부분 커버된 상태 — 이 부분은 안심해도 될 것 같음. 나머지 항목들(하드코딩 비밀값·`.gitignore`·Firestore 규칙·관리자 인증(클립2/9 문의처리 페이지 있다면)·AI API(예: 향후 도입 시)/솔라피 알림톡 같은 과금성 호출의 횟수 제한 등)은 다음에 코드 레벨에서 실제로 점검해볼 가치가 있음 — [[feedback_check_code_not_docs]] 원칙대로, 문서 말고 실제 코드를 열어서 확인할 것.

## 사주아이 유료강의7-1-4 글로벌진출

> 2026-08-11 추가. 강의 클립 9개 중 6번째 — PART 7, "글로벌 진출은 어떻게 하냐, 해외 결제는 어떻게 맞추냐"는 질문에 대한 답변.

**배경 문제의식**: "그냥 진출한다 쳐도 결제를 어떻게 맞추냐"는 질문을 많이 받았다고 함. 국내 카드만 받으면 해외 카드로는 결제를 못 받아서 글로벌 진출이 그림의 떡처럼 느껴지지만, 결제를 뚫는 방법이 몇 가지 있음.

**방법1: 미국 법인 설립 (스트라이프 아틀라스 활용)**
- 원래 미국 법인을 내려면 미국 비자·시민권·영주권이 필요하지만, 이를 우회할 수 있는 서비스가 **스트라이프 아틀라스(Stripe Atlas)**
- 비용이 꽤 나감(500~1,000달러 수준) — 미국은 원래 이런 비용이 비싼 편
- 진출 여력이 있다면 스트라이프 아틀라스를 통해 델라웨어 법인을 원격으로 설립하고 세금번호(EIN)를 발급받으면, 그 번호로 스트라이프 결제 모듈을 달 수 있음 → 해외에서도 결제 가능, 수수료도 괜찮은 편
- 이미 미국에 거점이 있다면 스트라이프 아틀라스 없이 바로 그 거점으로 진행하면 됨
- **단점**: 은행 계좌 개설이 어려움 — 법인 설립은 됐는데 계좌 개설이 안 될 수 있음. 미국은 신용점수를 깐깐하게 봐서, 신용점수가 낮거나 해외에서 미국 계좌를 열 수 있는 방법을 따로 찾아봐야 함(여러 은행에 직접 연락하거나, 델라웨어 법인 은행 개설을 대행해주는 한국 CPA·법무법인 대행사를 통하는 방법 등)
- 법인을 세우면 미국 매출에 대한 미국 세금 신고 의무가 따라오므로 행정적 부담이 생김

**방법2: 미국 법인 없이 토스페이먼츠 해외결제 옵션 이용**
- 토스페이먼츠에 해외 결제를 처리할 수 있는 옵션이 있음
- **단점**: 최소 결제 금액 제한이 있었던 것으로 기억한다고 언급. 토스 PG 일반 심사에 더해 추가 심사가 필요함. 결제 옵션이 스트라이프(일반카드·애플페이 등 다양)만큼 많지 않고, 아직 시범적으로 하는 느낌
- 관심 있으면 토스페이먼츠 측에 직접 문의 권장

**방법3 (참고): 세금까지 대신 처리해주는 서비스**
- 요즘 세금(부가세)까지 대신 걷고 신고해주는 서비스가 유행 — 대표적으로 **레몬스퀴즈(Lemon Squeezy)** 같은 곳
- 스트라이프는 부가세 신고를 직접 해야 하는 반면, 레몬스퀴즈류는 부가세를 알아서 걷고 신고까지 해줘서 편함(다만 수수료는 좀 더 비쌈)

**글로벌 진출 시 챙겨야 할 점**
- 단순 번역이 아니라, 현지인이 관심 있어하는 키워드·문화적 감성에 맞는 **로컬라이제이션**이 꼭 필요
- 예: CTA(버튼 문구) 하나도 한국·미국·일본이 다름 — 일본은 가타카나 표기가 많고 영어 문구를 그대로 쓰면 안 되는 등, 문화권마다 로컬라이제이션이 필요한 지점이 있음
- 웹이 아니라 **앱**이면 인앱결제를 쓸 수 있어서 결제 선택지가 훨씬 넓어짐 — 다만 인앱결제 수수료는 15~30%로 꽤 높음
- **정부 지원**도 활용 가치가 큼 — 수출 바우처, 해외 마케팅 지원사업 등 정부 지원 프로그램이 많음

### 오디오 핵심 요약

**"100만 유저를 어떻게 빨리 모으나요?"라는 질문에 대한 전제**
- 창업자 본인도 확실한 One Solution은 모른다고 솔직히 인정
- 100만·200만 유저 같은 숫자는 목표라기보다 **서비스가 지금 어디까지 왔는지를 보여주는 현재 상태(과도기적 지표)**에 더 가까움 — 유저 중 자발적 유입/운적 요소도 섞여있고, 실제 마케팅 퍼널로 들어온 비중은 분석하기 나름이라 "마케팅만의 성과"라 보기도 애매함
- 단계별로(10만→100만→1000만) 통하는 마케팅 방식 자체가 완전히 다르기 때문에, 공식화된 마케팅 이론은 AI나 다른 강의로도 배울 수 있고, 이 클립에서는 사주아이가 실제로 겪은 **경험적 사례** 위주로 공유

**핵심 포인트 ① 브랜딩**
- 마케팅·서비스 방향의 가장 핵심은 브랜딩 — 유저에게 전달하고 싶은 "이 서비스의 느낌"(카페에 갔을 때 분위기·손님·음식·소리로 느껴지는 것과 같은 개념)
- 정제된 문장: "서비스를 좋아해줄 사람을 계속 찾아나가고, 그 사람들을 찾았다면 더 좋아하게 만들 수 있도록 데이터를 분석하고 피드백을 받아 반영하는 것" — 이게 영업과 마케팅의 본질
- 사주아이는 **가설을 세우고 검증하는 루프**로 유저 반응을 모음(홍보보다 기획 단계에서부터 가설→검증→강화):
  - 가설1 "사람들은 한시적 공짜를 제일 좋아한다" → 희소성 있는 시간제한 무료 이벤트가 X(트위터)에서 실제 바이럴로 이어짐, 인플루언서/SNS 활동가들이 할인·공짜 정보를 정보성으로 자발 공유
  - 가설2 "이름보다 이미지로 각인시키자" → "사주아이"라는 이름 자체가 사주·아이 둘 다 보통명사라 검색 노출도 안 되고 확장성도 부족한 실패한 네이밍이었다고 자평. 이름 대신 뚜렷한 컨셉·이미지로 기억시키는 전략으로 전환 → 실제 바이럴은 "사주아이"라는 브랜드명보다 **"츄르사주", "고양이사주", "990원사주"** 같은 키워드가 훨씬 강한 바이럴 트리거였음
  - 가설3 "사람들이 MBTI처럼 자기 사주도 공유하고 싶어할 것" → 단, 사주는 운명적·미신적 요소 때문에 개인정보 노출에 민감할 수 있다고 보고 **공유 페이지에 익명 옵션**을 제공 → 실제로 X에서 본인/연예인 사주를 익명으로 올려 공유하는 방식으로 바이럴됨
- **바이럴의 함정("두바이 초콜릿 사태")**: 아무리 반짝 유행·바이럴이 터져도 브랜드가 지속 가능하게 자리잡지 않으면 그 유행은 금방 지나감 → 특정 상품의 반짝 바이럴만으로 살아남기는 어려움 → 지속적 성장 동력의 근본은 결국 **브랜딩**

**핵심 포인트 ② 창업자 스토리 = 가장 좋은 브랜딩 포인트**
- 아이템에 대한 관심은 식어도, "이 창업자가 다음에 뭘 만들지"에 대한 기대감은 남는다는 게 핵심 이유

  - **스레드(Threads)**: 조금 더 캐주얼, 꾸준히 얘기하면 들어주는 사람이 있는 채널, 완전 익명은 아니고 "대표" 직함은 유지하며 창업 뒷이야기를 캐주얼하게 풀기 좋음
  - **인스타그램**: 이미 상업화된 느낌이라 스토리를 다듬지 않고 날것 그대로 올리면 브랜딩으로 잘 안 이어짐

**핵심 포인트 ③ 컨셉과 디테일**
- 브랜딩은 결국 하나의 세계관·느낌이기 때문에 작은 디테일 하나하나(사주아이는 고양이 컨셉 — SNS 홍보물 톤, 디자인 톤까지 일관되게 유지)에서도 느껴질수록 좋음 — 이렇게 리치하게 만들수록 타겟 소비자 만족도가 높아짐

**핵심 포인트 ④ 트래픽 없어도 꾸준히 업로드**

## 사주아이 유료강의6-2-1 SEO/AEO ⭐가장 중요 (에스더님 지정: "6번 파트 3개가 가장 중요한 홍보법")

> 2026-08-11 추가. PART 6의 두 번째 클립 — SEO(검색창 노출)와 AEO(AI에게 물어봤을 때 우리 상품을 소개해주는지) 전체 방법론. 오디오 요약 + 캡쳐 8장 함께 저장.

### AEO란?
- SEO = 검색창에서 검색했을 때 상단에 뜨는 것
- AEO = GPT·Gemini 같은 AI한테 물어봤을 때 AI가 우리 상품을 소개해주는지
- 검색창과 AI봇이 인터넷상에서 데이터를 어떻게 수집·소화해서 유저 질문에 상단 노출하는지, 그 알고리즘을 이해하면 방법을 찾을 수 있음

### SEO 점수가 쌓이는 두 군데
1. **내 사이트 자체**에 쌓이는 도메인 SEO 점수
2. **발행 콘텐츠**(글·영상·뉴스 등) 하나하나에 쌓이는 콘텐츠 SEO 점수

### ① 사이트 SEO — Next.js 기본 5가지 필수 설정 (시간 걸리지만 한 번 쌓이면 도메인에 오래 지속됨)
1. **layout.tsx** — 사이트 전체를 구성하는 가장 큰 지도. 사이트 이름·타이틀·키워드·메타데이터·브랜드 정보·사용 언어 등을 꼼꼼히 넣을수록 봇의 사이트 이해도가 높아짐 — 클로드와 더블체크 권장
2. **각 페이지별 title** — 페이지마다 컨텐츠가 다르면 페이지별 타이틀도 따로 넣어야 페이지 하나하나가 노출될 수 있음
3. **sitemap** — 서비스가 어떤 URL 흐름으로 연결되는지 한눈에 보여주는 지도. 이걸 구글·네이버 같은 검색엔진에 직접 제출하면 indexing이 훨씬 쉬워지고 추적도 쉬워짐 — 클로드에게 만들어달라고 요청 가능
4. **robots.ts** — 크롤링 봇이 접근하면 안 되는 URL(예: 로그인 없이 볼 수 있지만 개인정보가 담긴 "공유하기" 화면)을 지정하는 파일. 이게 잘못 설정돼서 다 막혀있으면 다른 걸 아무리 잘해놔도 검색창에 노출 자체가 안 됨 — 로봇 설정 꼭 확인 필요
5. **OG 이미지(미리보기 이미지)** — 카톡·트위터·인스타 등에 링크 보낼 때 뜨는 미리보기 이미지. 플랫폼별로 계속 테스트해보고, 특정 SNS에서 안 뜨면 클로드에게 "이 SNS 미리보기가 안 뜬다"고 요청하면 해당 플랫폼 규격에 맞는 태그를 다시 만들어줌

**CSR vs SSR 렌더링 이슈**: 브라우저에서만 그리는 CSR 방식은 자바스크립트를 실행해야 내용을 볼 수 있는데, 구글봇은 자바스크립트 실행까지 하지만 네이버나 다른 AI봇들은 대부분 그렇게까지 하지 않음 → 바이브코딩 시 클로드에게 "CSR 방식으로 렌더링되는 페이지가 있는지" 확인 요청, 있으면 서버에서 HTML을 미리 만들어 보내는 방식(SSR)으로 전환 요청해야 SEO봇이 내용을 읽을 수 있음

**사이트맵 등록**: 만든 사이트맵을 구글·네이버·빙·다음 등 검색엔진마다 각각 등록(구글은 서치콘솔에 등록 페이지 있음, 네이버도 동일, 빙·다음은 소유권 확인 없이 바로 올릴 수 있는 곳도 있음) → 등록 후 약 1주일 정도 indexing 여부를 트래킹 → 안 되면 다시 바이브코딩으로 돌아가 사이트맵/키워드를 수정하며 피드백 반영

**신뢰도(백링크)**: SEO 점수에서 가장 중요한 건 "이 사이트가 얼마나 믿을만한 곳인지" — 언론기사·매거진·위키 등 공신력 있는 곳에서 링크를 걸어주는 백링크가 최고(창업자는 노마드코더 사이트가 그런 역할을 했다고 언급). 백링크를 받으면 그 사이트의 SEO 점수를 일부 가져올 수 있고, 점수를 못 받더라도 노출 빈도 자체는 높아짐

**점수 확인 방법**:
- 사이트 점수: Google Search Console, 네이버 Search Advisor에서 트래픽·노출 정도 확인
- 도메인 점수: Ahrefs(DR)·Moz(DA)·Semrush 등으로 대략 가늠(유료가 많아 굳이 볼 필요 있나 싶은 정도라고 언급, DR·DA는 구글 공식 수치가 아니라 업체 추정치라 참고용으로만 사용해야 함)
- 속도: PageSpeed Insights에 URL 입력해서 로드 속도 확인 — CDN·이미지 용량 등으로 느리면 SEO 점수에 악영향 + UX에도 직결

### ② 발행 콘텐츠 SEO/AEO
사주아이처럼 사이트를 직접 운영하는 입장에서, 발행 콘텐츠는 일종의 홍보물 — "어떻게 하면 이 홍보물을 잘 뿌릴 수 있을까"라는 관점.

**롱테일 키워드 전략**: 상위 20%의 인기·대중적 키워드는 경쟁이 너무 심한 레드오션이라 차라리 포기 — 나머지 하위 80%를 이루는 비인기·니치·뾰족한 "롱테일" 키워드를 공략하는 게 오히려 매출 임팩트가 더 클 수 있음. 블랙키위나 네이버 키워드도구로 특정 키워드 관련 롱테일 키워드 추천받기 (예: "다이어트"는 너무 인기 많은 메인 키워드 → "30대 직장인 저녁 다이어트 식단"처럼 좁히면 경쟁이 낮으면서도 리치한 롱테일이 됨). 이상적인 기준: 경쟁 "낮음"이면서 월 200번 넘게 검색되는 저평가 키워드. 검색량 자체보다 "이 사람이 뭘 원해서 검색했나"라는 의도가 더 중요 — 좁은 키워드가 경쟁이 약해 위에 뜨기 쉽고 정작 살 사람이 옴

**채널별 발행 전략**:
- **위키(나무위키, 위키백과)**: 홍보성 절대 금지, 완전 제3자적·객관적 정보성만 올려야 함 — 다만 AI가 답할 때 거의 그대로 인용하기 때문에 SEO/AEO 소스로 굉장히 좋음. 롱테일 키워드 중심 + 서비스에 대한 객관적 정보 삽입 추천
- **블로그(티스토리, 워드프레스, 인블로그(inblog))**: 인블로그는 구글 노출에 특히 강함. 네이버 블로그는 네이버 생태계 안에서 점수를 많이 줌. 단, 글 쓴다고 다 상위노출 되는 게 아니라 롱테일 키워드 + 글의 품질(뒤에서 다룸)에 따라 크게 좌우됨
- **매거진(브런치 등)**: 공신력은 있지만 진입장벽이 있음 — 전문성 있는 분야(사주아이는 사주, 다른 분야는 금융·건강 등)를 정보성으로 쓴 뒤 작가 신청 필요. 한 번 뚫으면 SEO 점수도 높고 플랫폼 인증에 따른 신뢰도까지 확보되는 좋은 자산
- **네이버 생태계**(한국인 타겟이면 거의 필수):
  - 지식인: 오래된 채널이라 outdated되면 잘 안 보이지만, 최근 글 위주로는 은근히 점수가 강해서 위에 잘 뜸 — 답글 다는 것도 홍보 효과 좋음
  - 네이버 프리미엄콘텐츠: 브런치와 비슷한 구조, 전문성+독자층 있으면 작가 신청(유료·무료 기고 모두 가능), AEO 점수를 높게 줌 — 한 번 뚫어두면 좋은 자산

**구글 공식 "유용한 콘텐츠 만들기" 가이드 핵심 (구글이 공식 발표한 문서 참고)**:
- 사람을 위해 쓴 도움되는 글, "AI 티" 안 나는 글, 직접 작성한 글(따라하지 않고 반복되지 않고 정말 도움되는 글)이 SEO 점수를 높게 받음
- 육하원칙에 따라 누가·왜·어떻게 작성했는지가 잘 드러나야 하고, 글의 구조가 명확해야 함
- 신뢰가 가장 중요 — 정보의 출처, 정보 품질, 얼마나 꾸준히 올리는지, 채널 자체가 지금까지 쌓아온 신뢰도까지 종합적으로 판단
- E-E-A-T(경험·전문성·권위성·신뢰) 4가지가 높을 때 SEO 점수 상승 — 디자인이나 정보 규격을 얼마나 잘 갖췄는지도 신뢰 판단 기준에 포함

**메타 태그 작성법**: H1(큰 제목)에 글의 대주제를 명확히 담기 / 메타 설명은 한글 50자 안팎으로 키워드를 넣고 클릭하고 싶게, 페이지마다 다르게(순위에 직접 영향은 적지만 검색결과 문구·스니펫과 클릭률을 좌우) / 타이틀·서브타이틀·CTA 문구, 롱테일 키워드 선택에 따라 클릭률이 크게 좌우됨

**백링크**: 다른 공신력 있는 사이트가 우리 사이트를 인용·소개해주는 백링크 — 개수도 중요하지만 품질이 더 중요. 창업자는 롱블랙·아웃스탠딩·에스콰이어 같은 매거진에 사주아이가 언급됐을 때 체감적으로 순위가 가장 크게(앞 페이지로 넘어올 정도로) 올랐다고 언급. 댓글 도배 같은 인위적 백링크는 좋지 않음

**AEO/GEO 트래킹(AI가 나를 인용하는지 추적)**: 원리는 간단 — 정해둔 질문을 매주 AI에 돌려서 내 브랜드가 답변에 나오는지 체크. 대표 유료 도구는 Profound(사주아이도 도입 예정, MCP 방식). 돈 안 들이려면 ChatGPT·Perplexity에 직접 물어보는 것도 방법

**결론**: 사이트 SEO + 콘텐츠 SEO 둘 다 챙겨야 장기적으로 트래픽과 브랜딩을 확보할 수 있음. 사이트는 천천히 쌓이는 것이고, 콘텐츠는 꾸준히 하다 보면 자산이 되어 스노우볼링됨.

**다음 클립 예고**: SNS별로 어떻게 활용하면 좋을지(마케팅 전문가는 아니지만 아는 선에서 간단히 다룰 예정)

1. **"내 사이트 점수, 어떻게 확인하나"**: 가장 정확한 건 무료 도구(구글 서치콘솔+네이버 서치어드바이저에서 실제 검색 노출 확인). 도메인 점수는 Ahrefs(DR)·Moz(DA)·Semrush로 대략 가늠. 속도도 점수라 PageSpeed Insights를 한 번씩 확인. DR·DA는 구글 공식 수치가 아니라 업체들이 매긴 추정치라 흐름 참고용으로만 사용
2. **"언제, 어떤 검색어를 노릴까"**: 사람들이 찾긴 하는데 경쟁은 덜한 말을 노려라. 블랙키위나 네이버 키워드도구로 한 달 검색량 확인. 경쟁이 '낮음'이면서 월 200번 넘게 검색되는 말부터 노리는 게 현실적. 넓은 말 말고 좁혀라 — '다이어트'는 이미 큰 사이트가 차지, '30대 직장인 저녁 다이어트 식단'처럼. 검색량보다 "이 사람이 뭘 원해서 검색했나"가 중요, 좁은 말은 경쟁이 약해 위에 뜨기 쉽고 정작 살 사람이 옴
3. **"어디에 올리나 — 검색이랑 AI가 읽는 곳"**: 위키(나무위키·위키백과 — 실리면 검색에서도 위에 뜨고 AI가 답할 때 거의 그대로 인용) / 블로그(티스토리·워드프레스·velog·인블로그) / 매거진(브런치·퍼블리·아웃스탠딩·요즘IT — 진입장벽 있지만 실리면 신뢰도+홍보) / 네이버 안(포스트·카페·지식iN·프리미엄콘텐츠 — 네이버 안에서 검색·질문으로 들어오는 사람을 잡기 좋음)
4. **"검색엔진이 아니라 사람을 위해 써라"** (Google「유용한 콘텐츠 만들기」 인용): 순위 노리고 만든 글 말고 사람에게 진짜 도움되는 글을 우대. 스스로 누가(저자)·어떻게(제작 과정)·왜(목적) 만들었는지 점검하라고 함, AI로 썼으면 밝히는 게 좋음. E-E-A-T 중 '신뢰'가 가장 중요, 건강·돈 같은 민감한 주제(YMYL)엔 더 엄격
5. **"제목 태그와 메타 설명 쓰는 법"** (인블로그「메타 태그 작성법」 인용): H1(큰 제목)은 그 글의 대주제를 분명히 담기. 메타 설명은 한글 50자 안팎으로, 키워드 넣고 클릭하고 싶게, 페이지마다 다르게. 순위에 직접 영향은 적지만 검색결과 문구(스니펫)와 클릭률을 좌우
6. **"AI가 나를 인용하는지 추적하기"** (Conductor「2026 AEO/GEO 트래킹 도구」 인용): 원리는 간단 — 정해둔 질문을 매주 AI에 돌려 내 브랜드가 나오나 체크. 대표 도구로 Profound. 돈 안 들이려면 ChatGPT·Perplexity에 직접 물어보면 됨
7. **"채널별로 · 네이버 프리미엄콘텐츠 — 전문성으로 승부하는 곳"**: 경제 인사이트처럼 깊이 있는 글을 연재. 구독을 유도하면 네이버가 검색에서 밀어줌. 무료 글로 사람을 모으고, 일부는 유료로 돌려 수익도 냄
8. **"채널별로 · 인블로그(inblog) — 구글 노출에 강한 곳"**: 내 도메인으로 글을 올릴 수 있어서 사이트 점수로도 함께 쌓임. 제목이랑 설명만 넣으면 메타태그가 알아서 들어감. 서치콘솔 연결이랑 사이트맵 제출까지 가이드가 있음. 그래서 인블로그는 CH.1(사이트 점수)이랑 CH.2(콘텐츠 점수)를 한 번에 쌓을 수 있는 채널

### 오디오 핵심 요약

**채널 확장에 대한 원칙**: 창업자도 여러 SNS를 갖고 있지만 하나가 안 되면 새 채널을 벌리고 싶은 유혹이 있음 → "하나부터 제대로 하자"고 스스로 다짐. 여러 채널을 동시에 다 챙기기는 힘드니, 페르소나를 다르게 분류해서 관리 여력이 될 때 채널을 분기하는 방식이 좋음

**공통 원칙 — 알고리즘이 보는 것**
- 릴스든 카드뉴스든 올린 뒤 **첫 30분** 반응이 가장 중요 — 개인 채널에 퍼뜨리고 친구들에게 좋아요를 요청해서 초반 트래픽을 몰아줌
- 알고리즘은 단순 좋아요·리포스트보다 **시청시간**(얼마나 오래 봤는지, 끝까지 봤는지, 반복재생했는지)과 **저장하기**(친구에게 공유하고 싶은 게시물인지)를 더 중요하게 봄
- 플랫폼 자체 에디터/툴(인스타 비디오 에디터, 인스타가 미는 배경음악 등) 사용 시 점수가 약간 높아지는 것 같지만 결정적인지는 불확실
- 끝까지 보게 만드는 짧은 영상(7~15초)이 조회수가 잘 나옴 — 첫 1~2초의 화면 전환·공감 문구·신선한 구도가 핵심, 얼굴이 안 나와도 움직임/이동이 있으면 좋음, 초반 후킹이 지루하지 않아야 흐름이 이어짐

**X(트위터) 특화 전략**
- 내 글만 올리면 반응이 없음 — 다른 사람 글에 계속 답글을 달아야 함, 시간의 70%는 답글에 쓰는 게 정석
- X는 발행-소비를 넘어 소통(댓글·리포스트) 중심 알고리즘
- 3D(스레드 이어달기) 기능 — 이전에 바이럴됐던 글을 이어받아 계속 살려나가는 방식이 X에서 활성화돼있음, 다만 쉽지 않음(이전 글이 잘 됐어도 다음 스레드가 안 될 수도 있음)
- 단발 포스팅보다 계속 서사를 설명해나가는 스레드 흐름을 사람들이 즐김, 자주 꾸준히 올리는 게 핵심
- 체감상 수요일~금요일 저녁이 잘 터지고 주말은 트래픽이 약함
- 창업 뒷이야기는 X보다 스레드가 더 잘 먹힘 — X는 개인 서사보다 서비스와 댓글 다는 사람들 간의 친근함을 활용한 카피라이트가 더 효과적
- 2026년부터는 X도 AI(Grok)가 노출을 정함, 영상은 유튜브 링크 걸지 말고 X에 바로 업로드하는 게 유리

**채널별 성격 요약**
- 릴스/쇼츠/틱톡: 짧은 밈 형식이라 조회수는 잘 나오지만 구매 전환·지속 구독 전환 효과는 약함
- X: 대화를 통한 초기 팬 모으기·친근감 형성에 유리, 댓글·"우리끼리 하는 얘기" 식이 잘 먹힘
- 스레드: X보다 조금 더 인사이트·공감대·목적성이 있어야 함 — 창업하면서 느꼈던 비하인드 스토리 풀어내기 좋음
- 링크드인: 자주는 안 썼지만 구체적 수치+성과+느낀점+누구 도움 받았는지의 성장 과정을 올렸을 때 가장 뷰가 잘 나옴
- 인스타 피드: 조회수·팔로워보다 "브랜드 분위기 전달"에 초점 — 서비스에서 느끼는 브랜드를 피드 디자인·콘텐츠 기획으로도 느끼게 하는 방향

**유료광고 시작 후 보게 된 숫자들 — 용어 정리**
- **메타픽셀**: 심어서 누가 실제 구매까지 이어졌는지 추적
- **ROAS(광고비 대비 매출)**: 광고비 1원 썼을 때 매출이 얼마 나왔는지 — 사주아이는 최소 2배를 목표로 잡음
- **CPA**: 결제 유저 한 명으로 전환시키는 데 드는 돈 — 생각보다 비쌈, LTV(고객이 평생 쓰는 돈)보다 CPA가 낮아야 남는 장사
- **CTR(클릭률)·CPM(노출당 비용)**: CTR 기반 과금(당근광고·네이버 키워드광고 등)은 클릭이 일어나야 과금되고, CPM은 노출만으로 과금돼서 단가가 CTR보다 낮음 — 함께 쓰기도, 하나만 쓰기도 함
- **퍼널**: 타겟팅한 전체 유저 → 클릭하는 사람 비율 → 결제하는 사람 비율로 점점 좁아지는 깔때기 구조 — GA로 각 단계에 데이터 시드를 심는 게 최선
- **전환율**: 본 사람 중 실제 구매 비율
- **CAC**: 한 명 데려오는 데 드는 돈 / **LTV**: 그 사람이 평생 쓰는 돈 — 업셀링·패키징이 LTV를 높이는 핵심

### 📸 캡쳐 저장 — 광고·홍보글 스타일 참고용 (7장)

1. **"어느 채널이든 결국 보는 건 비슷해요"**: 올리고 첫 30분이 제일 중요. 반응 붙으면 알고리즘이 "오 이거 좀 되네" 하고 더 뿌려줌. 좋아요 개수보다 사람들이 얼마나 오래·끝까지 봤는지를 더 쳐줌. 요즘 제일 센 건 공유량·저장 — "이거 친구한테 보내야지" 싶은 게 이김. 직접 만든 콘텐츠를 좋아함, 틱톡 로고 박힌 영상을 인스타에 올리면 오히려 묻힘
2. **"끝까지 보게 만드는 게 전부예요"** (인스타릴스·유튜브숏츠·틱톡): 짧게 만들기(7~15초) — 짧으면 다시 돌려보게 되고, 그게 좋은 신호가 됨. 6초를 끝까지 본 게 60초를 3초만에 넘긴 것보다 나음. 첫 1~2초에 딱 붙잡아야 함, 여기서 스크롤하면 끝. 사람들이 퍼 나르는 건 결국 공감가거나 의외거나 웃긴 것. 인스타는 피드·릴스·스토리·탐색이 각각 다른 기준으로 굴러감 — 릴스는 끝까지 보는지, 탐색은 저장·공유, 스토리는 답장 체크
3. **"X(트위터)는 이렇게 굴러요"**: 내 글만 올리지 말고 큰 계정 글에 답글을 많이 달기. X는 답글을 훨씬 높게 쳐줘서 시간의 70%는 답글에 쓰는 게 정석. 스레드(여러 개 이어쓰기)가 제일 셈, 글 하나하나가 따로 퍼져서 도달이 몇 배로 불어남. 리듬은 내 글 주 서너 개 + 답글 매일 열 개 남짓. 수요일~금요일 오전이 잘 터짐. 창업하면서 겪은 뒷이야기가 여기선 잘 먹힘, 여기도 올리고 30분이 승부. 2026년부터는 X도 AI(Grok)가 노출을 정함, 영상은 유튜브 링크 걸지 말고 X에 바로 올리기
4. **"채널마다 성격이 달라요" 표**: 릴스/숏츠/틱톡=폭발적으로 퍼짐(짧고 끝까지 보는 영상·밈) / X=대화·초기 팬 모으기(답글·스레드·창업 뒷이야기) / 스레드=솔직한 내 이야기(창업하며 느낀 것들) / 링크드인=신뢰와 성과 쌓기(과정·성과 기록, 주 2~3개) / 인스타피드=브랜드 분위기(결과 카드·감성 이미지)
5. **"돈 내고 광고할 땐 이 숫자들을 봐요(메타=인스타·페북)"**: 먼저 광고 목적을 '전환(구매·가입)'으로 잡고, 메타픽셀을 심어서 누가 실제로 샀는지 추적 — 그래야 알고리즘이 살 사람을 찾아줌. 제일 중요한 건 ROAS, 광고비 1원 써서 매출이 얼마 나왔냐는 것. 서비스면 2~3배, 쇼핑몰이면 4배는 나와야 남음. CPA는 한 명 전환시키는 데 든 돈 — 이게 그 고객이 평생 주는 값보다 싸면 남는 장사. 클릭률(CTR)·노출당 비용(CPM)은 광고 소재·타겟이 괜찮은지 볼 때 확인. 사람 데려오는 게 목적이면 클릭률을, 파는 게 목적이면 ROAS를 먼저 봄
6. **"자주 나오는 말들, 쉽게 풀면"**: 퍼널은 깔때기 — 많은 사람이 보고 → 일부가 눌러보고 → 또 일부가 사는 식으로 점점 좁아짐. 전환율은 본 사람 중 실제로 산 비율(흔히 말하는 '구매 전환율'). CAC는 한 명 데려오는 데 든 돈, LTV는 그 사람이 평생 주는 돈 — LTV가 CAC보다 커야 사업이 굴러감. 그 외 ROAS(광고비 대비 매출), 리텐션(다시 오는 비율)도 자주 나옴
7. **"채널 하나부터, 숫자를 보면서."**: 다 하려 말고 잘 되는 하나를 키우고, 감이 아니라 숫자로 판단하기

**How to apply (점운):** jeomun.com도 강의에서 언급된 애드랍(A드랍) 지면을 이미 사용 중이라는 점이 사주아이와 겹침 — 향후 광고 지면을 추가로 붙이거나 의뢰할 때 CTR/CPM 개념을 바로 적용할 수 있음. ## 사주아이 유료강의5-4 전체 운영 비용 관리 (Firebase & Gemini API 서버 비용 절감 가이드)

### 핵심 요약

**제일 중요한 전제 3가지**
1. 예산 알림(Budget Alert)은 "알림"일 뿐 요금을 자동으로 막지 않음 — 트래픽 급증을 구글이 알아서 차단하지 않고, 알림도 최대 며칠 늦게 옴
2. 무료 할당량(Spark/무료 티어)은 하루 또는 월 단위로 리셋됨(예: Firestore 읽기는 하루 5만 회, 매일 태평양시간 자정 초기화)
3. 과금은 대부분 "사용량"에 비례 — Firestore는 읽은 문서 수, Gemini는 토큰 수, App Hosting은 트래픽·연산 시간 기준. 비용 절감=불필요한 사용량 줄이기가 핵심

**Cloud Firestore** — 저장 용량보다 읽기·쓰기·삭제 "작업 횟수"가 요금의 대부분. 쿼리 결과 문서 1개=읽기 1회. 무료 한도: 저장 1GiB, 읽기 하루 5만회, 쓰기·삭제 하루 2만회, 전송 월 10GiB(매일 리셋, 프로젝트당 DB 1개만 무료). 초과 시 읽기 10만회당 $0.03, 쓰기 10만회당 $0.09. 절감법: limit()로 필요한 개수만 조회, offset 대신 커서 기반 페이지네이션, 오프라인 캐싱, 실시간 리스너(onSnapshot) 안 쓰면 해제, count() 집계쿼리 사용, 쓰기는 batch로 묶기, 데이터 비정규화로 읽기 횟수 자체를 줄이는 구조 설계, 안 쓰는 색인 삭제+TTL, 보안규칙의 get()/exists()도 읽기로 과금됨에 유의

**Firebase App Hosting** — Cloud Run(연산)+Cloud Build(빌드)+CDN 대역폭이 각각 과금. 2025-08-01부터 무료 한도 초과 시 과금 시작. 무료: 대역폭 월 10GiB, Cloud Run CPU 18만 vCPU-초, 메모리 36만 GiB-초, 요청 200만건, 빌드 2500분, 로깅 50GiB. 절감법: minInstances 0으로 스케일투제로, 캐시 적중률 높이기(캐시된 대역폭이 더 쌈), 응답 크기 압축, 빌드 트리거 관리, CPU/메모리 과다 설정 안 하기. apphosting.yaml에서 minInstances/maxInstances/cpu/memoryMiB/concurrency 직접 설정 가능

**Firebase Authentication** — MAU(월간활성사용자) 기준 과금, 기본인증(이메일/소셜/익명)은 월 5만 MAU까지 무료. 유료 구간: 5만~10만=MAU당 $0.0055 등 단계적 하락. ⚠️ 비용폭탄 포인트 2가지: ①전화번호(SMS) 인증은 무료티어 안에서도 무료 아님(건당 $0.01~0.06+), SMS 어뷰징(toll fraud) 공격 위험 — App Check + 허용 국가 제한으로 대응. ②Identity Platform(기업용 SSO) 켜면 MAU당 $0.015에 무료는 단 50 MAU뿐 — 실수로 켜지 않도록 주의

**Gemini API** — 입력/출력 "토큰" 수 기준 과금, 출력이 입력보다 훨씬 비쌈. Flash·Flash-Lite는 무료(Pro는 2026-04-01부터 유료 전용). 무료 티어 속도제한 분당 5~15회, 하루 약 1000회. ⚠️ 무료 티어는 구글이 입력 데이터를 서비스 개선에 활용할 수 있음 — 민감 데이터는 유료 티어 사용. 유료 요금(100만 토큰당): Flash-Lite 입력$0.10/출력$0.40, Flash 입력~$0.50/출력~$3, 상위Flash 입력~$1.50/출력~$9, Pro 입력~$2/출력~$12(200K 초과 시 상승). 절감법: 작업에 맞는 가장 싼 모델 선택(Pro는 Flash-Lite보다 10~20배 비쌈), 컨텍스트 캐싱으로 반복 입력 비용 최대 90% 절감, 급하지 않은 대량작업은 Batch API(50% 할인), maxOutputTokens로 출력 제한, 프롬프트 다이어트, "생각 토큰(thinking tokens)"도 과금됨에 유의, 개발·테스트는 무료 티어에서, 무한루프·API키 유출 방지(키를 프론트엔드·공개저장소에 노출 금지)

**비용 모니터링**: Firebase 콘솔 → Usage and billing → Budgets & Alerts에서 예산 알림 설정(초기엔 1%/5%/50%처럼 낮게, 운영 앱은 Actual 50%/100%+Forecasted 150% 권장). 진짜 자동 차단을 원하면 Cloud Billing 예산+Pub/Sub+Cloud Function으로 "예산 초과 시 결제계정 비활성화"를 직접 구성해야 함(앱이 실제로 멈추니 신중할 것). App Check로 봇·스크립트의 무단 호출(Firestore 읽기·SMS·함수호출) 비용을 막을 수 있음

**How to apply (점운):** jeomun.com은 Firestore가 아니라 **Firebase Realtime Database(RTDB)**를 쓰고 있음([[project_firebase_vs_supabase_decision]]) — 이 클립의 절감법 대부분(limit/커서/count()/batch/비정규화)은 Firestore 전용 개념이라 RTDB에는 직접 적용 안 됨(RTDB는 동시연결수+대역폭+저장용량 기준으로 과금 구조가 다름). 다만 원칙(①예산알림은 자동차단 아님 ②과금은 사용량 비례 ③App Check로 어뷰징 방지)은 RTDB에도 동일하게 적용됨 — App Check 켜져 있는지 확인해볼 가치 있음. Gemini API 부분은 jeomun.com이 "API 호출 최소화, 템플릿 기반" 원칙을 이미 지키고 있어 당장은 해당 없지만, 향후 AI상담 앱처럼 실시간 API가 필요해질 경우 Flash-Lite 우선 사용+컨텍스트 캐싱+Batch API 원칙을 그대로 적용할 것.

### 10 - 구글 로그인 구현하기 (프롬프트 원문)

design.md·BRIEF/PLAN·CLAUDE.md 규칙 준수. `.env.local`에 Firebase client 값(NEXT_PUBLIC_*)이 이미 채워져 있다는 전제로 로컬에서 실제 로그인이 되는 상태를 목표로 함. 만들 파일 7개:
1. `src/components/auth/AuthProvider.tsx` — 현재 유저·로딩 상태를 앱 전체에 제공하는 Context Provider, onAuthStateChanged로 구독, Provider 밖에서 useAuth 쓰면 명확한 에러
2. `src/hooks/useAuth.ts` — 현재 유저·로딩 상태를 가져다 쓰는 훅
3. `src/components/auth/LoginButton.tsx` — 구글 로그인(signInWithPopup+GoogleAuthProvider), 성공 시 redirect 파라미터 있으면 거기로 없으면 /dashboard로 이동, users.ts 저장 함수 호출해서 Firestore에 유저 기록
4. `src/components/auth/LogoutButton.tsx` — 로그아웃 후 / 로 이동
5. `src/lib/firestore/users.ts` — 로그인 유저를 users/{uid}에 저장/업데이트(merge), 필드: uid/email/displayName/photoURL/createdAt(최초만)/lastLoginAt(매 로그인)
6. `src/app/layout.tsx`를 AuthProvider로 감싸고, AppHeader의 로그인 버튼을 실제 LoginButton으로 교체 — 로그인 상태면 헤더에 유저이름+LogoutButton, 비로그인이면 LoginButton
7. `src/app/login/page.tsx` — 로그인 안내 화면(왜 필요한지+LoginButton), 비로그인 유저가 유료CTA 눌렀을 때 이 페이지로 오고 redirect 파라미터로 로그인 후 원위치 복귀

마무리 규칙: design.md 최우선, npm run build(또는 npm run verify)로 확인 후 에러 수정, 끝나면 (1)만든 파일 목록 (2)로컬 로그인 테스트를 위해 Firebase 콘솔에서 켜야 할 체크리스트(Authentication 시작/Sign-in method에서 Google 사용설정/승인된 도메인에 localhost 확인/Firestore 생성여부) (3)로그인 성공 확인법(헤더 표시+Firestore users 컬렉션 확인) 정리

**How to apply (점운):** 이 네 프롬프트는 design.md/BRIEF.md/PLAN.md 3개 문서가 미리 준비돼있다는 전제로 동작하는 템플릿 — jeomun.com처럼 이미 완성된 서비스보다는, 앞으로 만들 신규앱(8월 바이브코딩 챌린지용 4개: 오늘의핑계·나쁜운세·귀찮음지수·오늘뭐먹지, [[project_session_2026_08_03]] 참고)이나 그 다음 앱(AI상담 등)을 "0에서부터" 만들 때 그대로 재사용하면 랜딩+온보딩+무료샘플+로그인까지 초기 골격을 빠르게 잡을 수 있음. 단, 점운 프로젝트는 Firestore가 아니라 Firebase RTDB를 쓰므로 `src/lib/firestore/` 헬퍼 부분(users.ts 포함)은 실제 적용 시 RTDB 문법으로 바꿔야 함. 구글 로그인(10번)은 jeomun.com이 지금은 전화번호 기반 무회원 구조라 당장 적용 대상은 아니지만, 나중에 회원가입 시스템을 도입하게 되면([[project_pending_decisions]] 점운 PASS 통합 구조 참고) 이 템플릿을 그대로 재사용할 수 있음.
